# Model-proposed, human-validated invariant pairs — implementation plan

Status: foundational design, revised 2026-09-30. The custom participant-app and database portions below have been superseded by the chat-only grouped review workflow in [`CHAT_GROUP_REVIEW_PLAN.md`](CHAT_GROUP_REVIEW_PLAN.md). This document remains authoritative for the pair rubric, per-run controls, PACS split/evaluation safeguards, provenance, and Hugging Face/GRIT export validation.

## Purpose and boundaries

Add a dedicated **Validate** participant flow and a researcher console to the existing PACS web app. An agent searches a broader part of the PACS training population than the CAPTCHA grid permits, proposes a pair, and writes a checkable explanation. A human first judges the images without that explanation, then sees it and may revise the judgment. The old Play/Review/Analyzer records and APIs continue to work; this study uses its own record types and exports. Human-accepted pairs can later be mapped into GRIT's common pair format.

This is a test of pair **acquisition, validation, and collection quality**, not just a contest for the highest approval rate. The current CAPTCHA's nine-option limit is a plausible constraint on pair quality, but its effect on GRIT remains a hypothesis. Different PACS domains encourage visual/style variation; domain difference by itself does not prove a useful spurious intervention.

The PI's workshop paper models a pair's feature difference as useful spurious variation plus noise, and its robustness argument depends on **both semantic consistency and diversity of the difference vectors**. Its Remark 2 warns that a spurious direction absent from collected pairs cannot be identified; repeated changes in a single style feature cannot cover every shift. The pilot's 42 PACS triplets are a coarse coverage scaffold, not a mathematical certificate that the pairs span the relevant spurious subspace. See the local GRIT workshop manuscript (not bundled; see the [GRIT project](https://github.com/inouye-lab/GRIT)) and the [PACS benchmark description](https://domaingeneralization.github.io/).

## Pair rubric and response protocol

The proposer should look for the same **task-relevant subject configuration** across two images, with an identifiable change in medium, texture, palette, shading, or another plausibly task-irrelevant feature. PACS class equality is an eligibility constraint, not sufficient evidence of semantic equivalence. **Class, count of target-class subjects, and activity/pose must match in the first pilot.** A person alone versus a crowd, or a stationary horse versus one jumping, fails even when the class label matches. Viewpoint and articulation may differ only when the same activity/pose remains defensible; unclear cases are `unsure` or model abstentions. Similar background or composition does not invalidate an otherwise useful photo–sketch pair. Before generation, write class-specific examples and borderline cases for the seven PACS classes, including a coarse activity/pose vocabulary; do not improvise exceptions after seeing condition results.

The model may evaluate semantic agreement and style difference together. Its selection rule must refuse clear semantic mismatches regardless of how different the styles look. For hard-to-interpret or abstract images, it must state the uncertainty or abstain if no defensible candidate exists. Its reported confidence is a model estimate, not a calibrated probability or ground truth.

The proposer prompt should make it inspect each promising image **before** committing: describe the target-class subject count and coarse activity/pose for the anchor and candidate, name the visible style or contextual change, test whether the claimed invariant meaning survives that change, and reread its final explanation against both images. These intermediate checks can be stored as structured observations and mismatch flags; the participant receives only the concise final explanation. Do not reward the model for choosing a pair when the correct action is to abstain.

Use one structured output schema in all experimental conditions: chosen image handles or `abstain`; concise **what visibly matches**, **what visibly differs and why it is likely task-irrelevant**, **what remains uncertain**; an optional confidence estimate; and explicit tags for observations inferred from metadata rather than the pixels. Do not request or expose a full chain-of-thought transcript. Freeze the explanation before anyone reviews the pair; only reveal it after the first judgment is saved.

The human's first verdict is `accept | reject | unsure`, with a reason required for `reject/unsure` and optional for `accept`. After the explanation appears, record a second verdict and reason, including an unchanged verdict. The proposer never makes the human verdict. The first blind review is the only feedback source for adaptive search; the revised verdict is a separately analyzed outcome.

### Operational meaning of unclear cases

“Unclear” means the class/count/activity rule does not by itself say how to handle the image confidently. It includes target subjects hidden by overlap or cropping; a drawing too abstract to establish count or pose; a person or animal shown only as a head versus a whole body; ambiguous standing-versus-walking frames; and rigid categories for which “activity/pose” is not literal. The v1 rule is conservative:

- Count only visibly distinguishable instances of the target class; uncertainty about whether there is one or more leads to abstention.
- For people and animals, require the same coarse state: standing/stationary, walking, running, sitting, lying, jumping, riding/being ridden, or portrait/head-only. Viewpoint, facing direction, and exact limb geometry may vary within a state. If a single frame makes standing versus walking or another state materially ambiguous, abstain.
- For guitars, replace activity/pose with state/use: isolated/displayed, held, actively played, or detail-only. For houses, use whole exterior, partial exterior/detail, or interior.
- Incidental non-target objects do not change target count. Occlusion or abstraction is acceptable only if the required category, count, and state remain visually defensible.
- The model abstains rather than using a PACS label to rescue an interpretation that is not visible. The human may still mark a proposal `unsure` if they can see a plausible match but cannot verify it confidently.

These rules are deliberately coarse: they prevent obvious semantic changes while allowing useful viewpoint and rendering variation. The researcher should review and version them after a lab dry run, before comparing conditions. The exact first-condition text is stored in [`prompts/proposer_fixed_hidden_v1.md`](prompts/proposer_fixed_hidden_v1.md).

## Four-condition experiment

| Condition | Explicit PACS class/domain metadata to proposer | First-round feedback changes later search guidance |
|---|---:|---:|
| Fixed / hidden | No | No |
| Fixed / visible | Yes | No |
| Adaptive / hidden | No | Yes |
| Adaptive / visible | Yes | Yes |

**Default for a comparable four-condition run:** the researcher chooses one pinned multimodal proposer model and generation configuration for that run, and all four conditions use it. The model picker can offer more models in later runs. A different model in each condition may be useful for exploratory demonstrations, but then model effects are entangled with metadata/feedback effects; do not report the four-condition contrast as isolating those factors. The fixed conditions keep their instructions/search guidance unchanged while still proposing new images. The two adaptive conditions have separate feedback memories and prompt histories; fixed conditions never ingest review feedback. Each condition gets the same permitted image pool, image schedule, candidate retrieval method, call cap, token/image budget, and target coverage across the allowed class × unordered cross-domain categories. Balance which domain supplies the anchor within each category as well. Do not expose condition names to participants.

“Metadata hidden” means no **supplied dataset labels, domain strings, revealing filenames, URLs, or tool metadata** reach the proposer. The backend can still apply class and cross-domain constraints to candidate eligibility. Human feedback may naturally mention visible subjects or visual styles; preserve that criticism, but normalize explicit canonical PACS labels/domains or IDs into visually grounded language before using it to update a hidden arm. Store the original and normalized versions. The visible condition may use labels to interpret abstraction but must distinguish that inference from what can actually be seen.

Create a seeded, immutable schedule of `(class, unordered domain pair, anchor direction/ID, candidate-slate IDs and order)` before proposal generation. Reuse equivalent scheduled slates across conditions, keeping the class/domain mix balanced and making search versus prompt adaptation measurable. Generate proposal queues ahead of participant sessions to reduce waiting, but generate only the next adaptive batch under its currently frozen feedback version; pre-generation does not itself reduce total model compute. Randomize and interleave conditions for reviewers, avoid serving the same pair to the same reviewer twice, and record all assignments. An admin view may show conditions, budgets, queue progress, and acceptance; the participant view must look identical in every condition.

## Per-run controls and protocol snapshot

The researcher console creates a new **run** with these controls. Presets make the common train-only pilot one click; an advanced menu exposes the separate settings. Save the complete selection, seed, source/image fingerprints, and a canonical config hash in the run record before its first proposal. A change after start creates a **new run or explicitly versioned exploratory segment**, never silently rewrites the protocol of already generated proposals or reviews. This preserves flexibility across runs without allowing post-hoc choice of the best-looking export rule.

| Run control | Default | Recorded interpretation |
|---|---|---|
| Proposer model | **One model across four conditions** | Provider/model revision, image input method, prompt template, generation parameters, and per-call cost accounting. Backend-held credentials; models offered by a provider-adapter registry. |
| Pair inclusion verdict | Initial blind `accept` | `initial` or `revised` for the run's GRIT export; both judgments and their transitions are always retained. |
| Adaptive update interval | 5 completed initial reviews **per adaptive condition** | Positive integer and feedback source/version. Fixed arms never update regardless of interval. |
| Proposal image scope | Existing PACS `train` split | Explicit split ID set or run-specific source-domain train pool; `val/test` are selectable only in a clearly labeled exploratory run that cannot claim an untouched evaluation on those images. |
| Evaluation policy | **PACS held-out-domain (`pacs_lodo`) for the first robustness series** | `pacs_lodo`, `within_domain`, or a prespecified compatible shift evaluation, with target domain/fold and evaluation image set recorded separately from proposal scope. Collection-only runs choose `none`. |
| Search and review budget | Paged candidate slate, balanced triplets | Schedule seed, retrieval/model call caps, proposal/reviewer quotas, and prompt-update controller version. |

The UI exposes **proposal pool** and **evaluation target** as separate selectors, since the same `train/val/test` word has different meanings in collection and model testing. Show a run summary before launch: permitted proposal domains/splits, protected evaluation images/domains, available triplet count, selected model, judgment rule, and update interval. Reject a configuration that puts protected evaluation images in proposal inputs, retrieval, adaptive feedback, GRIT fitting, or hyperparameter selection. For an all-four-domain browsing run, train/val/test can be inspected separately; changing the split is a new run and its results remain tagged with that scope. For a comparable four-fold PACS result, create a **series of four runs** that share the selected model, verdict rule, cadence, retrieval budget, rubric, and analysis plan, differing only in which domain is held out and their resulting source pools. Allow differing settings across folds for exploration, but do not aggregate them as one controlled comparison.

Offer three clear presets above the advanced controls: **Collection** (`train`, all four domains, 42 triplets, no GRIT test); **PACS fold** (one target domain, source-`train` proposals and fitting, source-`val` model selection, 21 triplets, entire target domain protected); and **Exploratory/debug** (an explicitly selected split or domain, no untouched-test claim). The PACS fold preset can generate a matched four-fold series. This makes the toggles useful for different research questions without pretending that a `val/test` collection run remains an independent test of itself.

## Broader-search acquisition pipeline

1. Freeze the existing PACS source revision, split map, local JPEGs, ordered embedding IDs, and retrieval configuration. The asset audit found **9,991 unique IDs/JPEGs/aligned embedding IDs: 7,993 train, 1,000 validation, 998 test**. Build a **run-specific** search index exclusively from the proposal image scope and fail closed if the real manifest, split assignment, image bytes, or index alignment is missing. The default scientific run uses `train` only; a PACS held-out-domain run further excludes its entire target domain. A deliberately exploratory `val/test` proposal run is labeled contaminated for any evaluation reusing those images. Source images currently live under `web/public/pacs`; CLIP embeddings and ERM probabilities already exist, but neither a high score nor class agreement proves invariance. The current ERM probe was fitted on train rows from **all four domains** and must be retrained source-only or excluded as a feature/retrieval input in a strict held-out-domain run.
2. For each scheduled anchor/triplet, assemble a broad, bounded slate from the permitted partner domain, class, and run scope. **Provisional pilot:** up to 128 distinct eligible images, offered in pages of at most 32 with a recorded mix of CLIP-nearest retrieval and seeded random/diversity sampling. Some cells are smaller (the local `sketch/house` train cell has **64** images), so use all available eligible images rather than repeating IDs, and report the slate size by triplet. The model may inspect further pages within a fixed four-page/call budget and abstain when none is defensible. Hold the slate, retrieval policy, page order, and budget identical across conditions for a given scheduled anchor; record which images were actually viewed. Retrieval scores are backend provenance, not model-facing metadata in either arm.
3. Pass **image bytes** under session-local opaque handles and neutral filenames to the proposer, never image paths that encode `domain/class`. In visible runs, add class/domain fields explicitly. Keep alias-to-canonical-ID mappings and probabilities server-side. Parse the response against the shared schema, validate that both IDs belong to the run's permitted proposal pool and scheduled triplet, and store the exact candidate order, viewed pages, model output, explanation, and abstention/error status. The existing browser manifest exposes labels, domains, image paths, and scores; do not use it as a model-facing tool in the hidden arm.
4. Reject malformed or duplicate outputs for retry under a fixed retry cap. Store model/provider version, prompt and rubric hashes, retrieval-policy version, generation settings, candidate-schedule seed, elapsed time, token/image usage, and cost. A PRNG seed does not fully replay stochastic external API calls: **the exact inputs and returned outputs are the audit record**.

Keep generation and adaptive prompt revision on the FastAPI backend so API credentials and condition labels never enter browser JavaScript. Use a provider adapter so a model can be replaced without changing the study record or UI. The current `vlm_eval/vlm_model.py` evaluates a nine-choice CAPTCHA and can fall back to CLIP scoring; it should not be treated as the new image proposer. Record failed searches and abstentions; hiding them would inflate apparent proposal quality and obscure hard PACS categories.

## Feedback adaptation

The **run-selected** update interval defaults to **five completed first reviews per adaptive condition**. Freeze each adaptive prompt for that many completed first verdicts/reasons, then update the next batch; another run may choose a different positive interval. The fixed arms accumulate matched reporting windows but never change their guidance. The update controller may add versioned search guidance (for example, avoid pairing one person with a crowd in abstract art). It cannot quietly relax the run's semantic rubric, expand to protected images/domains, use explanation-assisted revised verdicts, or inspect final GRIT test results. If feedback suggests changing the rubric itself, record a proposed specification change for researcher review and a separately versioned protocol/run.

Write each batch's start/end times, included feedback-event IDs, prompt diff/hash, controller output, and frozen version. Reviews of already queued proposals remain attributed to the old prompt. Keep the adaptive queue bounded by the run's next update interval so it can respond on the chosen cadence. Analyze performance by feedback/prompt version as well as condition. The hidden-arm normalizer must remove canonical PACS terms and researcher metadata from the model-facing guidance without discarding the participant's visual criticism.

## Participant and researcher interfaces

- Add a direct-link **Validate** participant page in the React app; it may be reachable through a tab for researchers, but research subjects should land on this flow directly. Show two square images, simple verdict controls, and a short reason field. Hide model explanation, confidence, condition, dataset labels, and researcher scores until the initial verdict has been durably acknowledged by the backend. Then reveal the three-part explanation and ask for the revised judgment. Show a concise completion/save status and let a participant resume an interrupted session. Cache unsent form edits locally for retry after a transient network failure; the server remains the authoritative record.
- Preserve the existing `Play`, `Review`, and `Analyzer` stores. A new study store handles assignments and staged judgments. Do not reuse `GameRecord` as a proposal record or silently count model-proposed pairs as CAPTCHA-curated pairs.
- Add a researcher console with a **new-run form** for proposer model, initial/revised GRIT verdict rule, feedback update interval, separate proposal/evaluation split settings, target-domain fold/series, retrieval budget, and quotas. Show the resulting protected pools and 21/42 triplet count before launch. After launch, display the immutable run settings alongside condition/batch/coverage counters, abstentions, audit trail, prompt versions, reviewer progress, and export controls. Researcher-only data must be served through authenticated routes; the existing six-character shared-Review API is a lab-trust convenience, not an adequate boundary for condition blinding or subject data.

## Backend data and reproducibility

Introduce `/api/studies/...` routes beside the existing review API. **Provisional local-pilot storage:** SQLite with WAL, migrations, and atomic transactions; design repository interfaces for later Postgres hosting. Existing `server/data/<code>` review files remain untouched. Write judgments before returning success; retry requests use idempotency keys so network errors cannot create double reviews. Separate participant and researcher roles, use pseudonymous reviewer IDs, and keep model keys in server-side environment variables. Queue assignments and explanation reveals must be server-enforced, not only hidden in the UI: a participant's pre-verdict response contains image bytes/handles and rubric only, and the reveal endpoint refuses access until the initial verdict is committed.

The minimum entities are `Study/ProtocolVersion`, immutable `RunConfig`, optional `EvaluationSeries`, `Condition`, `CandidateSlate`, `GenerationAttempt`, `Proposal`, `PromptVersion`, `FeedbackBatch`, `Assignment`, and append-only `ReviewEvent`. A proposal stores immutable `(runId, target fold, anchorId, partnerId, class, domain pair, source split, candidate IDs/order, viewed pages, explanation, uncertainty, model/prompt/feedback versions, costs)`; the reviewer record stores `initialVerdict/Reason/At`, `explanationRevealedAt`, `revisedVerdict/Reason/At`, and review durations. Keep exact proposal/review timestamps and separate image IDs from bytes. Export the run config and protected evaluation IDs/fingerprints with every derived dataset.

Implement a narrow server-enforced state machine: `queued → assigned → initial_saved → explanation_revealed → revised_saved`, with an explicit `abstained/failed` branch for generation. Suggested routes are researcher-only study creation/generation and exports, participant assignment fetch, idempotent initial-verdict submit, explanation reveal, revised-verdict submit, and session resume. The initial fetch must never serialize explanation, model confidence, condition, or hidden metadata; a direct reveal URL before `initial_saved` must fail. Events retain the previous state and protocol version so a crash or duplicate submit is unambiguous.

For new studies, use a **SHA-256 fingerprint of the full source manifest and checksums for all source images used by the study**, not only the current game's FNV hash of ordered IDs. Persist the source revision, split policy, embedding alignment fingerprint, and image-byte hashes. A study can be reconstructed from its recorded slates, viewed images, calls, outputs, and event log even if the proposer model later changes.

## Outcomes and exports

Primary pilot outputs: (1) blind accept/reject/unsure rates; (2) blind-to-revised judgment transitions; (3) downstream GRIT robustness with the **same frozen learner/evaluation procedure** on comparable accepted-pair collections; (4) coverage and redundancy; (5) initial/reveal-stage human review time; and (6) model calls, latency, and cost per valid or useful pair. Analyze abstention and confidence calibration as secondary measures. Prespecify the metadata main effect, adaptation main effect, and their interaction, with reviewer and triplet stratification; this is a four-condition pilot, not a claim of statistical power. Set a sample and pair budget after a cost/throughput dry run but before inspecting condition outcomes. Define denominators before running: reviewed proposals for acceptance, all attempted generations for abstention, and accepted pairs meeting the run's selected initial/revised GRIT rule. Human agreement and confidence are observations, not proof of invariance.

Pair quality and collection quality are distinct. Measure coverage across **42 triplets in all-domain collection runs or 21 source-only triplets per PACS fold**, and within-triplet subject count, activity, viewpoint, style, and ambiguity strata where feasible. Record repeated image IDs, duplicate pairs, and embedding-near duplicates. On a frozen feature representation, summarize the accepted-pair difference-vector covariance, effective rank, and eigenvalue spread as **descriptive diversity diagnostics**; these are not proof that the unknown spurious subspace has been recovered. Do not choose pairs or GRIT hyperparameters against held-out test outcomes. Sample independent audits of accepted/rejected/unsure proposals and generation attempts; do not treat a few checked examples as certification of the whole process.

Export three linked artifacts: a lossless proposal/event archive for replay; a one-row-per-proposal, one-row-per-judgment research dataset with condition and provenance (Hugging Face Parquet with native image columns when published); and a one-row-per-human-accepted-pair GRIT input according to the run's **initial or revised verdict selector**. Both verdicts remain available for prespecified sensitivity analysis. Do not feed this study's JSON through the old CAPTCHA `build_hf_dataset.py` unchanged. Hold GRIT architecture/hyperparameters and pair counts fixed across conditions, compare matched class/domain coverage, and keep validation selection separate from final evaluation.

The first release must include a **new proposal exporter** that writes `invariant_pairs.parquet` with one accepted pair per row. It should follow the proven image-embedding pattern in the old exporter while preserving the new study schema. Required columns include stable pair/run/proposal IDs; condition, fold, prompt/feedback/model versions; selected verdict rule and both judgments; anchor/partner IDs, class/domain/split and native Hugging Face `Image` columns; semantic/spurious/uncertainty explanations; reviewer timing; manifest/image fingerprints; and acquisition costs. Keep rejected/unsure proposals, abstentions, candidate slates, and event history in linked audit Parquet/JSONL artifacts rather than pretending they are GRIT training pairs.

An export is marked **Hugging Face ready and GRIT compatible** only after an automated gate succeeds:

1. Load the Parquet through both PyArrow and `datasets.load_dataset("parquet", ...)`; verify the declared schema, one row per unique pair, nonempty row count, and absence of empty struct columns.
2. Decode both native image columns for sampled rows and verify every embedded image checksum against the frozen source snapshot. Generate a dataset card that declares the Parquet data file so the Hugging Face viewer renders anchor and partner images.
3. Verify each exported row was accepted under the run's frozen initial/revised rule, both IDs belong to the permitted proposal pool, class matches, domains differ, and no protected target-domain/evaluation image appears.
4. Resolve every pair ID into the frozen GRIT feature index; compute finite difference vectors with the expected feature dimension; reject missing IDs, duplicate pair IDs, NaN/Inf values, zero-image payloads, or schema/version mismatches. Report pair count, class/domain coverage, repeated-image rate, and descriptive difference-vector rank/spectrum without treating those diagnostics as proof of pair quality.
5. Round-trip the exported Parquet into the lab's GRIT pair loader in a smoke test. Export success means the loader can consume the exact file without manual column renaming or conversion. A simple class-match percentage is insufficient for this claim.

Write each export to a new run/version directory or content-addressed filename, plus a `latest` pointer if helpful; never silently overwrite an earlier scientific artifact. The first implementation stops at locally validated Parquet and supporting files for lab use. Uploading to a Hugging Face dataset repository remains an explicit later action.

## Downstream evaluation: what each split choice answers

The **first robustness target is PACS leave-one-domain-out**, in a four-run series. The original PACS benchmark trains and validates on source domains and tests on the whole held-out domain; that asks whether pairs help a classifier cope with a *visual domain it never saw in this fold*. [Li et al., ICCV 2017](https://openaccess.thecvf.com/content_ICCV_2017/papers/Li_Deeper_Broader_and_ICCV_2017_paper.pdf) used a 9:1 source train/validation split. **This study keeps the project's existing deterministic 80/10/10 split within each domain/class.** In each fold, source-domain `train` images supply proposals and fitting, source-domain `val` images supply model selection, and source-domain `test` images remain unused by primary selection (they may be declared in advance as a secondary seen-domain diagnostic). Every image in the target domain is protected as unseen-domain test data regardless of its existing 80/10/10 label. Report this as the study's protocol rather than an exact replication of the original 9:1 PACS protocol. Testing **human-validated PACS pairs** in GRIT is also a new acquisition experiment; the PI paper's PACS section used source-domain augmentations in a semi-supervised setting, so its published numbers are not a direct comparator for this pair-proposer study.

For fold `target=sketch`, for example, the proposer and GRIT see only eligible source-domain images/pairs from photo, art painting, and cartoon. Only **3 unordered source-domain pairs × 7 classes = 21 triplet types** are available in that fold. The entire sketch domain is excluded from candidate retrieval, pair proposal, reviewer feedback used for adaptation, source-only probe fitting, GRIT training, rank/hyperparameter selection, and source validation; it is opened once for final test. Repeat with each of the four domains as target. The all-domain CAPTCHA or a finished 42-triplet study cannot simply be filtered after generation: its model or adaptive prompts may already have learned from the fold's nominal target domain. Use independent, isolated prompt histories and queues for every `(fold, condition)`; the four-condition design therefore has **16 condition-fold queues** across the series. Each fold can still use the same four experimental conditions and one selected proposer model.

The current all-domain ERM probabilities are unsuitable as model-facing retrieval or classifier inputs for a strict fold because that probe fitted target-domain `train` examples. Refit source-only probes if needed, or keep ERM out of this pipeline. A frozen externally pretrained encoder can be declared as shared infrastructure, but its image index and any data-fitted components must be restricted to source images; target feature extraction is reserved for final evaluation. Model selection, including GRIT rank, uses **source validation only**, not the target domain. Compare GRIT against ERM or another prespecified baseline with the same encoder, source training images, hyperparameter budget, and random seeds. Match the human-accepted pair count and class/source-domain coverage across conditions without consulting target accuracy; report any condition unable to meet the quota rather than silently changing it. Report target accuracy per held-out domain and the four-fold mean, along with source validation performance, class-level breakdowns, uncertainty across seeds, and pair acquisition costs.

The other evaluation settings answer different questions:

| Evaluation setting | Proposal/fitting pool | Protected test pool | Claim it supports |
|---|---|---|---|
| Existing within-domain split | `train` across all four domains; select on `val` | Existing `test` across all four domains | Held-out-image generalization to **already seen** domains, a useful pipeline check but not unseen-domain robustness. |
| Controlled PACS shift | `train` across all four domains; select on `val` | Prespecified label-preserving style/background perturbations of untouched `test` images | Response to that engineered shift; validity of the perturbation and its strength must be checked before comparing results. |
| Independent dataset | Source data and compatible invariant pairs from that dataset, or an explicitly separate transfer study | Its own locked target/test set | External replication only if task labels and evaluation design align. PACS's seven-class pairs do not automatically form a direct Waterbirds-style binary task benchmark. |

A split toggle is therefore a **protocol selector**, not a shortcut from `train` to `test` in the same pair search. Runs that propose from `val/test` remain useful for debugging or annotation research, but they cannot later claim that those images were untouched in an evaluation. The server should show the overlap and refuse a conflicting confirmatory configuration. Neither user-selectable model nor verdict rule nor feedback interval should be tuned against the held-out-domain test: choose them across fresh runs or source validation, and label post-test changes exploratory. [DomainBed's model-selection taxonomy](https://github.com/facebookresearch/DomainBed) makes this distinction explicit.

## Delivery sequence and acceptance checks

1. **Run-config and protocol design:** write seven class-specific semantic examples, define the first PACS held-out-domain series, and implement model/verdict/cadence/split/budget selectors with immutable config snapshots. Choose review population, source split policy, pair quota, and analysis contrasts before test inspection.
2. **Backend foundation:** migrations, roles, run/config and proposal/assignment/event APIs, idempotent writes, append-only audit, crash/rejoin recovery, fold-isolated prompt memory, protected evaluation pools, and deterministic candidate schedules. Verify no target-domain or protected-split image reaches proposer inputs, search indices, feedback, or fit in a confirmatory run; verify no cross-condition feedback and no explanation/condition leak before the initial verdict.
3. **Proposer pilot:** provider adapter + structured response validation, opaque image handles, paged up-to-128-image slates, abstention/retries, four isolated condition queues **per target fold**, and prompt versioning. Begin with the versioned fixed/hidden prompt, then derive the visible and adaptive variants without changing the base rubric. Dry-run a small balanced source-only sample with manually inspected images and cost accounting.
4. **Participant/researcher UI:** staged review with durable writes and resume, a direct participant link, researcher new-run/series form, generation dashboard, and export controls. Exercise network interruption, duplicate-submit, reviewer blindness, per-run setting changes, and illegal proposal/evaluation split overlap in a browser.
5. **Export and compatibility gate:** generate versioned proposal-ledger, judgment, and accepted-pair artifacts; build image-bearing Hugging Face Parquet; run schema/image/leakage/feature-index checks and the real GRIT-loader smoke test before calling an export compatible.
6. **Pilot study and analysis:** calibrate throughput with a prespecified small source-only batch across the available 21 triplets per fold; audit ambiguity and coverage; then run matched GRIT/ERM evaluation on the held-out domain using source-only model selection. Reserve all-four-domain 42-triplet inspection for separately labeled collection studies.
